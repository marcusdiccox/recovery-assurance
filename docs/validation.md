# Validation

This document distinguishes executed checks from configuration and future plans.

## Executed locally

- Windows, Python 3.12: **289 Python tests passed**, including real restic restores selected by full ID, abbreviated ID, and `latest` from a repository with multiple snapshots.
- Node.js: **6 dashboard tests passed**, including combined filters, incomplete timing summaries, empty evidence, and distinct failure reasons.
- Ruff: lint and formatting checks passed.
- Built the wheel and source distribution, with dashboard assets included in the wheel.
- restic **0.19.1**, downloaded from the official release; checksum-verified installer also exercised on Windows.
- Snapshot identity regressions verify that only a resolved full ID reaches restore, subfolders are preserved, invalid/missing/ambiguous lookups stop without restoring, lookup errors remain sanitized, and lookup/restore share a timeout budget. Resolved IDs survive a later restore failure and appear in exported HTML evidence.
- Named-profile checks run the actual CLI from another working directory and cover persisted outcomes and exit codes 0/1/2. They also verify config-relative local paths, unchanged remote URIs, duplicate/invalid settings, finite limits, UTF-8 BOM input, and preservation of directory symlink rejection. Both example profiles were parsed with the production loader.
- Baseline-loading regressions reject duplicate schema, files, paths, sizes, and checksum keys, including paths that collide after JSON escape decoding. Boolean/float schema versions are rejected before recording a drill. UTF-8 BOM input with Unicode paths produces valid recovery evidence. Actual direct/profile CLI subprocesses reject a conflicting-checksum baseline with exit code 2 and no appended run; both previously reported success with the same fixture.
- Baseline entry annotations, November 22, 2026: reproduced unchanged content being reported as changed when a valid file entry included an operator note. Three API/direct/profile regressions failed before comparing only required size/SHA-256 fields and then passed; two independent size/checksum mismatch guards already passed and remain green. Tests verify unchanged baseline bytes, preserved parsed annotations, exact full-manifest evidence fingerprint and stored passing CLI evidence. This does not add filesystem ownership/permissions verification.
- Failed baseline writes, November 24, 2026: actual JSON serialization errors reproduced partial output left behind. Six cleanup/retry regressions failed before the fix and then passed; two existing/replacement-file preservation guards already passed and remain green. Checks use real temporary files with injected disk-full write/close failures and interruption, plus actual nonfinite/unserializable values. They verify retry success, original exception propagation, unchanged existing/replacement content and capture CLI exit 2 without a leftover partial baseline. No filesystem was filled, and power-loss/hard-kill cleanup, hostile races and unknown file-identity filesystems were not exercised.
- Dataset-history checks cover labels on passed, failed, and error reports; CLI/API filtering; exact label matching with bound SQL parameters; filtering before the history limit; and unchanged legacy reports without a dataset field.
- Recorded dataset inventory, November 25, 2026: all 16 new cases failed before implementation and then passed. Store/actual CLI checks cover 204 real records for one label beneath more than 200 recent samples, stable latest-ID ties, stored-column ordering despite payload differences, case/Unicode/literal/empty labels, strict non-sample markers and invalid-label exclusion. Writable/write-protected prepared archives retain database bytes and directory contents. Empty eligible history returns `[]`; missing/invalid sources, malformed reports and invalid ordering types fail clearly without initialization. Duplicate-key fixtures use a single decoded interpretation for grouping. These synthetic stored rows are not usage or recovery-performance measurements.
- Pagination checks traverse 406 original records through real CLI/API pages, with tied timestamps, timestamp/ID ordering differences, a legacy unassigned row, and newer insertions between pages. Filtered history also crosses the 200-record boundary. Missing/empty cursors fail clearly, including when an empty-ID row exists, and SQL-like cursor IDs remain literal through the read-only Store and API.
- CLI list checks inspect writable and write-protected prepared archives through combined, filtered and paged reads, preserving exact reports, database bytes and directory contents. Rejected cursors also preserve the archive. Existing empty/unrelated files fail without initialization, while a missing history path retains first-use creation. Ten archive-safety regressions failed before selecting read-only access; the first-use compatibility guard already passed.
- Scheduling runbook, November 15, 2026: constructed Windows task action/settings definitions and exercised equivalent process arguments against synthetic data from an unrelated working directory, with spaces in absolute config/database paths. Observed exit codes 0/1/2 and exactly two persisted completed drills. Local links, PowerShell snippet syntax and POSIX wrapper syntax (via Git sh) passed. No task was registered or started by Task Scheduler; the Linux cron/flock recipe and timed/unattended account execution were not exercised locally.
- Local drill locks, November 16, 2026: real subprocesses verify that a held lock makes direct and profile invocations return 75 before input loading or database creation, without report output. Locks can be reused after passed, failed and erroneous invocations, and after terminating a separate holder; independent paths do not block one another. Invalid paths and aliases preserve existing content and do not start a drill. All 12 new cases failed before implementation and then passed. The Windows native lock was exercised locally; Unix locking is covered by the same process tests in the Ubuntu CI job. Updated runbook links and PowerShell/POSIX syntax were checked; timed schedulers and unattended accounts remain untested.
- Saved-evidence health checks, November 17, 2026: all 29 new cases failed before implementation and then passed. Actual CLI subprocesses cover fresh passing, latest failed/error, stale and absent evidence; filtering real evidence before more than 200 recent samples; deterministic ID tie-breaking; exact case-sensitive and SQL-like dataset labels; invalid policies and unusable latest metadata without falling back to old success. Existing prepared archives, including write-protected files, retain their bytes and directory contents. Missing/invalid histories are not initialized. Deterministic clock tests cover the exact age boundary and non-UTC timestamp offsets. This validates saved-evidence assessment, not deployed alert delivery or unattended scheduler execution.
- Expected-baseline checks, November 27, 2026: 23 initial cases failed before implementation; the final 26-case suite also covers unchanged age/outcome requirements when the baseline matches. Actual CLI/API checks cover matching evidence, changed content/annotations/creation time, canonical JSON formatting/key order/BOM, newer evidence against another baseline, sample-only or absent evidence, invalid manifests and unusable recorded fingerprints. Prepared writable/write-protected archives and manifests retain their bytes and directory contents. Ordinary checks preserve the previous JSON fields and accept legacy records without fingerprints. The full 289-test suite includes these checks and actual restic restores; this validates saved fingerprint comparison, not signed evidence, a live backup or a baseline catalog.
- Explicit multi-dataset monitoring, November 26, 2026: all 21 new cases failed before implementation and then passed. Checks cover all-healthy success; failed/error/stale/missing/sample-only evidence preventing combined success; exact deduplication/order/case; empty-selection rejection; later invalid evidence producing no partial JSON; archive preservation; invalid sources and age policies. The combined new/existing health suite passed 52 tests. Independent source review approved and separately checked valid empty labels, duplicate labels, every distinct missing label, and required CLI selection. These probes reuse single-check policy and do not certify an atomic cross-dataset snapshot or deployed monitoring service.
- Independent health-check review identified an ambiguity in manually inserted JSON with duplicate dataset/sample keys: SQLite selection and Python decoding could disagree and report healthy evidence for another dataset or a sample. Two raw-row CLI regressions reproduced exit 0 before the correction and exit 2 afterward. Selected evidence now revalidates its decoded dataset and explicit non-sample marker. This narrow consistency check does not authenticate history or provide general tamper detection.
- CLI export checks use actual subprocesses and stored passed/failed/error drills whose backup source has been removed. They verify exact JSON evidence, escaped standalone HTML, unchanged history, format selection, overwrite protection (including the history database), and clear failures for unknown IDs, missing/invalid databases, and missing output parents.
- Read-only export regressions cover write-protected JSON/HTML archives, unchanged database bytes and journal mode, URI-sensitive paths, rejected inserts and missing databases, and committed WAL evidence while a writer remains open. Real Windows extended-path exports and a portable UNC URI-conversion check cover the path issue found during independent review. The conversion check maps the SQLite call to a local fixture; end-to-end SMB access and physically read-only mounted volumes were not exercised.
- History-backup checks copy 206 records with an open WAL writer, compare exact stored rows and unchanged source journal mode, run SQLite quick_check on the standalone copy, and export a saved report from it. They cover read-only sources, empty history, invalid inputs, protected files/symlinks, timeout cleanup, both directions of source/output sidecar overlap, and pre-existing destination sidecars including dangling links. Independent review identified the sidecar collision risk; all 12 added regressions failed before its correction and then passed.
- CLI demo: three real drills on 25 synthetic files per drill, with recorded durations and deliberate integrity/time failures.
- Browser, November 4, 2026: inspected the redesigned dashboard at desktop and narrow viewport sizes. Verified combined filters, empty datasets, the verification guide, sample execution, selected-run exports, and keyboard focus moving to the inspector. The narrow layout stayed within the viewport, with the table scrolling independently. No browser errors or warnings were recorded.
- Independent read-only code review completed. The recursive-copy containment finding, SQLite cleanup, and misleading sample-summary message were fixed and covered by regressions.
- The interface redesign received a separate read-only review. Its desktop focus and secondary-text contrast findings were corrected; live keyboard verification confirmed that selecting a run focuses the inspector.

## Executed in GitHub Actions

The preceding release passed Windows and Ubuntu jobs with the Python suite, JavaScript tests, Ruff, and package build (run `41763108831`). CI installs a checksum-verified pinned restic release. [GitHub Actions results](https://github.com/marcusdiccox/recovery-assurance/actions) are the authority for each subsequent revision; workflow configuration alone is not execution evidence.

## Not executed / outside this release

- Docker build/run: Docker Desktop's Linux engine was unavailable locally.
- Azure provisioning, cloud-restic repositories, identity, RBAC, hosted authentication, and alerts.
- Full disaster recovery, application startup, database consistency, permissions/metadata, RPO, large-data performance benchmarks, or multi-user load testing.

The demonstrated metrics are small local-fixture measurements, not production recovery claims.
